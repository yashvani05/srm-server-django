1The plan, and why it is not "everything on Vercel"

Vercel runs your code as short-lived functions: they start when a request arrives and stop right after. That is perfect for a website and an API, but it means Vercel has no database, no Redis, and cannot keep a worker running.

About the workerOur BullMQ worker must stay running, which Vercel cannot do. So on Vercel the overdue check runs as a Vercel Cron Job every 24 hours (section 9). The BullMQ worker code is unchanged and can run on any always-on host if you want faster checks later.
Honest noteI tested all of this by running the API exactly the way Vercel runs it (as a function, in production mode, with only hosted-style settings), and by building the website the way Vercel will. I cannot log in to your accounts, so the first real deploy is yours. Section 11 covers the usual first-time problems.

2Put the code on GitHub

Vercel pulls your code from GitHub. Create an empty repository on github.com (no README, no .gitignore), then in your project folder:

git add -A
git commit -m "Service Request Management System"
git branch -M main
git remote add origin https://github.com/YOUR-NAME/YOUR-REPO.git   # use the address GitHub shows you
git push -u origin main
Safe by defaultThe .gitignore already keeps .env files and node_modules out, so your passwords are not uploaded. Never remove those lines.

3Create the database (Neon)

  1. On neon.tech create a project. Pick a region close to you (the same continent as Vercel's default is fine).
  2. Open Connection details. Turn Pooled connection ON and copy the connection string. It looks like postgresql://user:pass@ep-xxxx-pooler.region.aws.neon.tech/neondb.
    Paste it without anything after the ? (we turn on encryption with a separate setting).
  3. Create the tables and starting data from your laptop. Vercel never runs migrations. In the server folder: 
    cd server
export DATABASE_URL='PASTE-THE-NEON-URL-HERE'
export DB_SSL=true
npm run db:migrate      # creates all tables
SEED_ADMIN_EMAIL='you@yourcompany.com' \
SEED_ADMIN_PASSWORD='a-strong-password-1' \
SEED_EMPLOYEE_PASSWORD='another-strong-password-2' \
npm run db:seed         # roles, permissions, 2 demo users, 12 sample requests
    You should see migrated lines and no errors. Choose your own passwords here: this database will be public.

4Create Redis (Upstash)

  1. On upstash.com choose Create database (Redis). Pick the region closest to your Vercel region, and keep TLS on (default).
  2. On the database page find the TCP / ioredis connection string. It starts with rediss:// (two s's, meaning encrypted) and looks like rediss://default:PASSWORD@xxxx.upstash.io:6379. Copy it.
Free tier limitUpstash counts commands. Our cache, logout list and overdue check use very few. A worker that polls all day would use many, which is another reason the Vercel setup has no always-on worker.

5Deploy the API (Vercel project 1)

  1. On vercel.com: Add New → Project, and import your GitHub repository.
  2. Set Root Directory to server (click Edit next to it). Framework Preset: Other. Leave the build settings as they are: server/vercel.json already tells Vercel what to do.
  3. Open Environment Variables. You can paste this whole block into the first field and Vercel splits it into rows. Replace every value that starts with PASTE or MAKE-UP. 
    NODE_ENV=production
DATABASE_URL=PASTE-THE-NEON-URL
DB_SSL=true
DB_POOL_MAX=2
REDIS_URL=PASTE-THE-UPSTASH-rediss-URL
JWT_SECRET=MAKE-UP-A-LONG-RANDOM-STRING
JWT_EXPIRES_IN=1h
CORS_ORIGIN=https://temporary.example.com      # we fix this in step 7
SWAGGER_USER=apidocs
SWAGGER_PASS=MAKE-UP-A-STRONG-PASSWORD
TRUST_PROXY=1
ENABLE_BULL_BOARD=false
CRON_SECRET=MAKE-UP-ANOTHER-LONG-RANDOM-STRING
    To make a strong random value, run openssl rand -base64 32 in a terminal.
  4. Click Deploy. When it finishes, copy the address Vercel gives you, for example https://my-api.vercel.app.
  5. Check it: open https://my-api.vercel.app/api/v1/health. You should see "status":"ok". Then /api-docs asks for your docs user and password.

6Deploy the website (Vercel project 2)

  1. Add New → Project again, import the same repository.
  2. Set Root Directory to client. Vercel detects Vite by itself.
  3. Add one environment variable, using the API address from step 5: 
    VITE_API_BASE_URL=https://my-api.vercel.app/api/v1     # your API address + /api/v1
  4. Deploy, then copy the website address, for example https://my-web.vercel.app.
Important Vite ruleThe website bakes this address in when it is built. If you ever change VITE_API_BASE_URL, you must Redeploy the website for the change to take effect.

7Connect them

The API only accepts requests from the website's address. Tell it what that is.

  1. Open the API project → Settings → Environment Variables.
  2. Edit CORS_ORIGIN to your website address with no slash at the end: https://my-web.vercel.app.
  3. Go to Deployments → the latest one → ⋯ → Redeploy. (Environment variable changes only apply to new deployments.)

9The overdue check: a cron job every 24 hours

Vercel cannot keep our worker running, so the overdue check runs as a Vercel Cron Job once a day. It is already set up in the code. The only thing you add is CRON_SECRET (it is in the settings block in step 5).

  1. server/vercel.json contains a cron entry: "schedule": "0 4 * * *". Every day at 04:00 UTC (that is 06:00 in South Africa, before the working day) Vercel calls /api/v1/internal/cron/overdue-check on your API.
  2. Vercel adds the header Authorization: Bearer YOUR-CRON-SECRET by itself, because you set CRON_SECRET. The API refuses anyone without it (and the address does not exist at all if the secret is not set).
  3. The API runs the same check our worker runs: it flags requests that have been Open or In Progress for more than 24 hours, clears any flag that should not be there (a resolved request is never overdue), saves the time it ran, and refreshes the dashboard numbers.
What "once every 24 hours" means in practiceFlags are updated once a day, not the moment a request turns 24 hours old. A request that passes 24 hours at 05:00 is flagged at the next 04:00 run, so up to about a day late. The dashboard's Overdue card always tells the truth about this: it says "checked 7h ago". Marking a request Resolved or changing its status still clears its overdue flag immediately, with no waiting for the cron.

Check that it works

  • In Vercel open the API project → Settings → Cron Jobs. You will see the job listed. Click Run to fire it now.
  • Then open the website dashboard: the Overdue card should say checked just now.
  • Or from a terminal: 
    curl -H "Authorization: Bearer YOUR-CRON-SECRET" https://my-api.vercel.app/api/v1/internal/cron/overdue-check
# {"success":true,"message":"Overdue check completed","data":{"marked":0,"cleared":0,"durationMs":12}}

Change the time of day

Edit the schedule in server/vercel.json and push. Times are in UTC, and South Africa is UTC+2. For example 0 22 * * * runs at 00:00 in South Africa. Free (Hobby) Vercel accounts can run a cron job at most once a day, so keep it a daily schedule.

Want fresher flags later? (all optional)

Free

Check when people look

Add the setting OVERDUE_ON_DEMAND_SECONDS=60 to the API project and redeploy. Then opening the dashboard or the list also runs the check if the last one is over a minute old.

Free

External scheduler

A service such as cron-job.org can call the same address every few minutes with the header Authorization: Bearer YOUR-CRON-SECRET.

Paid

Vercel Pro

Change the schedule to * * * * * to run it every minute.

Own server

The BullMQ worker

Run npm run build && npm run start:worker in server/ on any always-on host, with the same DATABASE_URL and REDIS_URL.

10Security checklist before sharing the link

Your site is now on the public internet. Go through these.
  • Demo passwords. Step 3 used your own passwords. If you ever seed with defaults, admin@company.com / Admin@12345 becomes a public admin login.
  • Strong secrets. JWT_SECRET, SWAGGER_PASS and CRON_SECRET must be long and random, and never committed to GitHub.
  • API docs. They are behind a password. Keep it private.
  • Public sign-up. Anyone can register as an employee. That is how the app is designed, but know it before sharing widely.
  • Login rate limit. It counts per client IP inside each function instance on Vercel, so treat it as a speed bump, not a wall.

11If something fails

First look: Vercel → your project → Logs (or Deployments → the deployment → Functions). The error message is almost always there.

The API shows a 500 / "Invalid environment configuration"
A required setting is missing or malformed. The log names it. Common ones: JWT_SECRET shorter than 16 characters, SWAGGER_PASS missing (required in production), a DATABASE_URL that is not a valid postgres:// address.
Cannot connect to the database / SSL errors
Make sure DB_SSL=true, and that the Neon address has nothing after ?. Use the pooled connection string. If you see "too many connections", keep DB_POOL_MAX=2.
"relation ... does not exist"
The migrations were not run on this database. Repeat step 3 against the same DATABASE_URL you gave Vercel.
Every logged-in request gives 503
The API cannot reach Redis (it refuses to guess whether a token was logged out). Check REDIS_URL: it must start with rediss:// and include the password.
The browser console says "blocked by CORS"
CORS_ORIGIN must equal the website address exactly: https://, no trailing slash, no path. Fix it and Redeploy the API.
The website loads but login does nothing, or the page is blank
VITE_API_BASE_URL is missing or wrong on the website project. Set it, then Redeploy the website (it is baked in at build time).
A page refresh gives 404
The website's client/vercel.json must be present with the rewrite rule. Check the website project's Root Directory is client.
Vercel says "No Output Directory named public found"
The API project's Root Directory must be server, so Vercel sees server/vercel.json and the server/public folder.
The cron job returns 401 or 404
401 means CRON_SECRET differs from what the caller sends. 404 means CRON_SECRET is not set on the API project (the endpoint does not exist without it).
Overdue flags look out of date
With the daily cron they are refreshed once a day, so this is expected. The Overdue card shows when the check last ran. Click Run on the cron job (Settings → Cron Jobs) to refresh now, or see the optional faster options at the end of section 9.
