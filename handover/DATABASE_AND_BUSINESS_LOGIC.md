Evidence labels: **[code]**, **[ran]** (executed during this inspection), **[test]**, **[opinion]**.

## 1. How the schema is created
Schema is managed only by Django migrations (`makemigrations` generates, `migrate` applies). Migrations in the repo [ran `showmigrations`]:
- `accounts/migrations/0001_initial.py` — creates `users` (+ many-to-many tables `users_groups`, `users_user_permissions`).
- `service_requests/migrations/0001_initial.py` — creates `system_state` and `service_requests` with indexes and CHECK constraints.
Django's own apps (auth, contenttypes, admin, sessions) add their tables on `migrate`. After `migrate`, the `post_migrate` handler `sync_role_groups` (`service_requests/apps.py`) creates the ADMIN and EMPLOYEE groups and assigns the permissions from `accounts/roles.py::ROLE_PERMISSIONS`.
Database: PostgreSQL, database name `srm_django` by default (`DB_NAME`), separate from the Node app's `service_requests` database.

## 3. Meaning of the timestamps
- `created_at` — when the row was created. Never changes. (The assignment says "creation date".)
- `updated_at` — last save of any kind (edit, status change, flag change by the worker does **not** touch it because it uses `QuerySet.update()`, which bypasses `auto_now`) [code].
- `status_changed_at` — set at creation (= `created_at` default `timezone.now`) and **only** reset in `services.change_status` when the status actually changes. **This, not `created_at`, drives overdue.**
- `overdue_at` — when the worker set the flag (database `Now()`), cleared with the flag.

## 4. The overdue rule exactly as coded
A request is overdue when `status ∈ {OPEN, IN_PROGRESS}` **and** `status_changed_at < now() − 24 hours` (strictly older; exactly 24 h is not overdue). Implemented once, in SQL, in `service_requests/overdue.py::qualifies_as_overdue()` using the database clock (`django.db.models.functions.Now`) and `OVERDUE_AFTER_HOURS = 24` from `constants.py`.
- RESOLVED is never overdue (not in the status set).
- Status change (including reopening) → `status_changed_at = Now()`, `overdue = False`, `overdue_at = NULL` immediately (`services.change_status`). A reopened request starts a fresh 24 h clock.
- Editing title/description/etc. does not restart the clock.
- **Interpretation choice [opinion]:** the assignment says "Open or In Progress for more than 24 hours". I measured time **in the current status**, not since creation (so OPEN→IN_PROGRESS restarts the clock). The alternative (age since `created_at`) is simpler; if the interviewer expects it, change `status_changed_at` to `created_at` in `qualifies_as_overdue` and drop the reset in `change_status`. The Node README also documents this interpretation [README].
- The flag is **persisted** (a column), so it can lag the real time by up to one worker interval (60 s). The dashboard and the `?overdue=true` filter read the flag; no endpoint recomputes it live.
- Seed data sets the flag at insert time for items older than 24 h (`seed_demo.py`).

## 5. Dashboard calculations
`dashboard/services.py::build_summary()` — one query (`aggregate`) with `Count("id", filter=Q(...))`:
- `totalRequests` = all rows; `openRequests` = status OPEN; `inProgressRequests` = IN_PROGRESS; `resolvedRequests` = RESOLVED; `highPriorityRequests` = priority HIGH (any status); `overdueRequests` = rows with `overdue = true`.
- Counts are **org-wide** for both roles (an employee sees the whole organisation's totals, not just their own) [code; matches README "org-wide summary"]. [opinion] This is a product decision worth stating in the interview.
- `lastOverdueCheckAt` = `system_state.updated_at` for key `overdue_check.last_success_at`, read fresh from the DB on every request (not cached).

## 7. How data is read and written
- Insert: `ServiceRequest.objects.create(created_by=user, **data)` → INSERT. Update: `setattr` + `save(update_fields=[...])` → UPDATE of only those columns. Status change: UPDATE of status, `status_changed_at`, overdue columns. Delete: `.delete()` → DELETE. List: filtered/ordered queryset with `select_related("created_by")`, `.count()` for the total, then a LIMIT/OFFSET slice.
- Ordering `created_at DESC, id DESC` (stable pagination). Offset pagination — fine at this size; deep pages get slower on large tables [opinion].
