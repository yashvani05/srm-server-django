Our backend lives in server-django/. It exposes exactly the same API as the Node version, so the React app did not change. This page explains it in the order a request travels.

2. Follow one request: GET /api/v1/requests?overdue=true

  1. config/urls.py sends api/v1/ to each app's urls.py; service_requests/urls.py maps requests to RequestCollectionView.
  2. Authentication (accounts/authentication.py): reads the Bearer token, checks signature/expiry, checks the Redis denylist (logout), loads the user.
  3. Permission (get_permissions in the view): asks "does this user's role group hold requests.read?"
  4. Serializer (ListQuerySerializer): validates page, limit, status, overdue.
  5. Service (services.list_requests): admin sees all, employee only their own; builds the query and paginates.
  6. Response: core/responses.success() wraps data as {success, message, data}. Errors are wrapped the same way in core/exceptions.py.

3. The overdue job (Q2)

  • Rule: OPEN/IN_PROGRESS for more than 24h in the current status. Changing status restarts the clock and clears the flag at once.
  • Celery Beat is the alarm clock: every 60s it adds check_overdue to a to-do list in Redis.
  • Celery worker takes the task and runs overdue.run_overdue_check() in one DB transaction: flag newly overdue rows, heal stale flags, save "last success" time.
  • The dashboard shows that last-success time and reads counts from a Redis cache (60s). Any write clears the cache.

4. Run it (copy-paste)

cd server-django
source .venv/bin/activate
docker start srm-redis          # Redis
python manage.py migrate        # create tables
python manage.py seed_demo      # demo users + 12 requests
python manage.py runserver 8000 # API  (terminal 1)
celery -A config worker -B -l info --pool=solo   # worker + scheduler (terminal 2)
cd ../client && VITE_PROXY_TARGET=http://localhost:8000 npm run dev   # UI (terminal 3)

6. Questions the client may ask

QuestionAnswer
Why Django REST Framework?It is the standard way to build APIs in Django: serializers validate input, views handle HTTP, built-in auth/permission hooks.
Where is role checking?Roles are Django Groups holding permissions (accounts/roles.py); each view declares the permission it needs.
How does logout work with JWT?The token's id is stored in Redis until it would expire; every request checks it.
What if Redis is down?Dashboard falls back to the database. Auth fails closed with 503 because we cannot verify revocation.
Why a separate Celery process?The web server must stay fast; scheduled work runs elsewhere and survives web restarts.
Is the overdue job safe to run twice?Yes, it only updates rows whose flag is wrong, inside one transaction.
Tip: when lost, open service_requests/services.py first. It holds the business rules in plain readable Python.
