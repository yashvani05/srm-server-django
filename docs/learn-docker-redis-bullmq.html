1The big picture: a restaurant

Think of our project as a small restaurant. Each tool is one part of it.

Docker

The sealed lunch box

A ready-to-eat kitchen corner you can open anywhere. It lets us run Redis without installing anything.

Redis

The kitchen whiteboard

Quick notes anyone can read or wipe off. Very fast, but temporary.

BullMQ

Order tickets + a bell

A rail of tickets (jobs) and a bell that adds a new ticket every minute.

Worker

The cook

Takes one ticket at a time and does it. If the cook leaves, tickets wait.

Bull Board

The ticket screen

A web page showing how many tickets are waiting, done or failed.

PostgreSQL

The filing cabinet

Permanent records: users, requests, overdue flags.

The one sentence to rememberDocker runs Redis. BullMQ keeps its job list inside Redis. Bull Board draws a page from that job list.

2Docker

Software needs the right version and settings. "It works on my machine" is a classic problem. Docker packages a program with everything it needs, so it runs the same everywhere.

Image

The packaged program, frozen. Example: redis:7-alpine. Like a recipe with ingredients.

Container

A running copy of an image. Like a dish made from the recipe. You can start, stop and delete it.

Port mapping

6379:6379 means your computer's port : the container's port. A door from your house into the lunch box.

Volume

Storage that survives when the container is deleted. A shelf outside the lunch box.

Our docker-compose.yml, explained

Compose is just one file that describes the containers we want. This is the Redis part of ours:

services:
  redis:                          # a service called "redis"
    image: redis:7-alpine         # use the official Redis, version 7 (small build)
    container_name: srm-redis     # the name we use in our commands
    ports:
      - "6379:6379"               # your computer :6379  →  the container :6379
    volumes:
      - redis_data:/data          # keep Redis's data on a named shelf
Good to knowPostgreSQL is not in Docker for you. It is installed on your Mac. Redis is the only thing you run through Docker.

3Redis

Redis stores keys and values in memory. A key is a label, a value is what is written on the note. A note can have a timer that wipes it by itself.

The same commands, in the real thing

# then:
SET city Johannesburg       # write a note
GET city                    # read it
EXPIRE city 30              # wipe it in 30 seconds
TTL city                    # seconds left (-2 means it is gone)

4BullMQ

Some work should happen later or on a timer, with nobody clicking anything. BullMQ is a to-do list for that, stored in Redis.

Queue

The to-do list.

Job

One item on it, like "run the overdue check".

Worker

A program that takes jobs one at a time and does them.

Scheduler

The alarm clock: "add a job every 60 seconds".

An open-source package (@bull-board/express) that already contains a finished web page. We only give it our queue. In server/src/app.ts:

createBullBoard({ queues: [ourQueue] })

RedisInsight

A separate program in Docker

Made by the Redis company, downloaded as a Docker image. Our code never touches it. It is only a window into Redis.

Open it at http://localhost:5540.

What to tell the clientThe queue and the worker are our code. The dashboards are standard open-source tools that read what is in Redis.

What happens when you click "Create request"

  1. The website sends it to the API. The API first asks Redis: "is this login still valid?"
  2. The API saves the request in PostgreSQL.
  3. The API tells Redis to delete dashboard:summary, because the numbers are now out of date.
  4. Next time you open the dashboard: Redis has no note, so the API counts in PostgreSQL, stores the answer for 60 seconds, and shows it.
  5. Every minute, on its own, the scheduler adds a job. The worker flags anything open for more than 24 hours, saves the time it ran, and deletes the cached numbers if something changed.

Starting everything each day

open -a Docker               # 1. start Docker Desktop (wait for it to settle)
docker compose up -d redis   # 2. Redis
cd server && npm run dev     # 3. API      (terminal 1)
cd server && npm run worker  # 4. Worker   (terminal 2)
cd client && npm run dev     # 5. Website  (terminal 3)

To stop: Ctrl+C in each terminal, then docker compose stop.

7"Build it in front of us" plan

There is a ready-made kit in docs/live-demo/ (about 40 lines of code, its own Redis on port 6380). The whole thing takes about 10 minutes.

  1. Start a Redis. Say: "Docker lets me run Redis in one command." 
    docker run -d --name demo-redis -p 6380:6379 redis:7-alpine
docker exec -it demo-redis redis-cli
    Then type SET greeting hello, GET greeting, EXPIRE greeting 20, TTL greeting.
  2. Show caching. Run npm run cache. You will see a slow first answer (~1500 ms) and a fast second one (~1 ms).
  3. Show the queue. Three terminals: npm run board (open localhost:3010/board), npm run worker, then npm run add. Watch jobs complete, one wait 10 seconds, one fail three times, and one appear every 15 seconds by itself.
  4. Prove it is real. docker exec -it demo-redis redis-cli KEYS "bull:*". Say: "The queue is just notes in Redis."
  5. Show why the worker is separate. Stop the worker, run npm run add: jobs pile up. Start the worker: it clears them.
Practise twiceDo it once while reading, then delete the files and retype them from docs/live-demo/README.md without copying. Then it is yours.

Your 2-minute explanation

"Employees submit service requests in a React app. An Express API stores them in PostgreSQL. I use Redis for three things: caching the dashboard numbers for 60 seconds, remembering logged-out tokens so logout really works, and as the storage for a BullMQ job queue. A separate worker process runs every minute, finds requests that have been open or in progress for more than 24 hours, and marks them overdue. I run Redis in Docker so it installs with one command."

8Questions the client may ask

Why Redis and not just PostgreSQL?
Redis is much faster for small, temporary data, and its timers delete things automatically. PostgreSQL stays the permanent record.
What happens if Redis goes down?
Logins are refused with a 503 (on purpose, because we can't check for logged-out tokens), the cache is skipped, and the queue pauses. When Redis comes back, everything resumes by itself.
What if the worker stops?
The website keeps working. Overdue flags just stop updating and the dashboard shows "checked X minutes ago". Starting the worker catches up.
Why a separate worker process?
Website traffic and background work don't slow each other down, and each can be restarted or scaled on its own.
What stops two workers doing the same job twice?
The queue gives each job to only one worker, and the work is safe to repeat: it only changes rows whose flag is wrong.
How does the cache stay correct?
Every create, edit, delete and status change (and the worker) deletes dashboard:summary. The 60-second timer is a safety net.
Is the Bull Board page your own UI?
No. It is an open-source library. We mount it in our server and protect it with a password.
Why Docker?
One command gives everyone the same Redis, with nothing to install or configure.
